# ADR-001. Управление приоритетами каскада

**Статус:**  · **Дата:** 18.11.2026

## Контекст

В проекте участвуют две команды: Atlas UI и подрядчик (legacy-виджет, который нельзя удалять).
В DevTools мы зафиксировал два ключевых конфликта:
1. **Кнопка Primary:** стиль `#workbench .ui-button` (unlayered) перебивал `.ui-button--primary` из `@layer components` из-за ID и отсутствия слоя.
2. **Уведомление Danger:** глобальный класс `.is-danger` из `legacy.css` перекрашивал теги и уведомления, создавая утечку стилей между семействами.

## Рассмотренные варианты

| Альтернатива | Плюсы | Риски | Почему выбрали или отклонили |
|---|---|---|---|
| A. Всё в одном CSS-файле | Просто начать. | Хаос, невозможно отследить, кто перебивает кого. | **Отклонили:** не масштабируется и нарушает изоляцию. |
| B. БЭМ + регламент селекторов | Понятная методология. | Требует абсолютной дисциплины всех команд. Один опечатавшийся разработчик ломает всё. | **Отклонили:** сложно контролировать подрядчика. |
| C. @layer + токены + контракт компонента | Жесткая изоляция. Слои решают конфликт специфичности. Токены управляют темой. | Нужно переписать legacy и строго соблюдать порядок импортов. | **Выбрали:** Это стандарт современного CSS, который решает наши проблемы на уровне архитектуры. |
| D. Только CSS Modules | Локальные имена классов. | Требует сборщика (Vite/Webpack). Не решает конфликт с глобальным legacy-виджетом. | **Отклонили:** избыточно для текущего стека, не спасает от глобальных селекторов подрядчика. |

## Решение

* **Порядок слоёв:** `reset → legacy → tokens → base → components → states → utilities`.
* **Принцип специфичности:** Запрет на ID и `!important`. Все стили находятся в классах. Слои контролируют приоритет без использования весов.
* **Публичные классы и модификаторы:** API компонентов строится по схеме `block`, `block--modifier`. Модификаторы (например, `.ui-button--danger`) не должны влиять на другие компоненты.
* **Зависимость от селекторов родителя:** Ограничена. Компонент оформляет только свои прямые элементы и слоты, не всех вложенных потомков (изоляция).
* **Third party CSS:** Стили подрядчика (`legacy.css`) принудительно помещены в слой `legacy` (самый слабый после `reset`), а их селекторы ограничены контейнером `.legacy-widget`.

## Последствия и риски

При подключении новой библиотеки её нужно сразу обернуть в `@layer` (например, `layer(vendor)`). Если стили придут без слоя, они перебьют всё.
Регрессию можно обнаружить с помощью 18 структурных тестов (`npm test`), которые проверяют отсутствие `!important`, фиксированных `min-width` и наличие токенов.

## Два контрпримера

1. **Почему добавление !important не является решением проблемы?**
   Потому что `!important` ломает каскад и делает отладку невозможной. Два `!important` конфликтуют между собой, и победит тот, кто написан позже в файле. Вместо этого мы используем `@layer`.

2. **Где одного @layer недостаточно?**
   `@layer` не решит проблему, если внутри компонента используется жесткий селектор с ID или глобальный класс вроде `.is-danger`, который перекрашивает чужие элементы. Нужна также методология именования (БЭМ) и использование токенов для тем.
